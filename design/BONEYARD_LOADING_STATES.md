# Boneyard Loading-State Layer

Boneyard is the preferred loading-state tool for data-heavy React screens generated by the App Factory.

It is **conditional**, not a global dependency. Static pages and simple synchronous screens do not need it.

## When to use it

Use Boneyard when a screen has asynchronous content whose final layout is already known, especially:

- dashboards;
- tables and result lists;
- cards populated from APIs;
- job/application feeds;
- analytics pages;
- profile/detail screens;
- Suspense boundaries;
- authenticated app pages where loading-state layout shift would be distracting.

Do not add it merely for decorative placeholders on static marketing pages.

## React integration

Install only in products that need it:

```bash
npm install boneyard-js
```

Wrap async UI with a stable unique name:

```tsx
import { Skeleton } from 'boneyard-js/react'

export function AccountSummary({ data, loading }) {
  return (
    <Skeleton name="account-summary" loading={loading}>
      {data && <AccountSummaryCard data={data} />}
    </Skeleton>
  )
}
```

For Suspense-driven data fetching, prefer `BoneSuspense` where appropriate.

## Generate the bones

CLI option:

```bash
npx boneyard-js build
```

The generated registry must be imported once from the app entry:

```ts
import './bones/registry'
```

For our default Vite-based apps, the Boneyard Vite plugin may be used when continuous recapture during development is valuable. Keep it out of projects that do not need automatic capture.

## Authenticated screens

Prefer fixtures for capture rather than putting real production credentials into a skeleton-generation command.

When a page requires data, provide realistic non-sensitive fixture data so Boneyard can capture the resolved layout without depending on a live user session.

Never place production access tokens, session cookies, or secrets in committed Boneyard config.

## App Factory rules

- Loading UI must mirror the real content hierarchy rather than show generic bars everywhere.
- A Boneyard skeleton name must be stable and unique within the app.
- Re-run bone generation after meaningful layout changes to wrapped components.
- Commit generated bones/registry when the product build expects them at runtime.
- Test mobile, tablet and desktop breakpoints used by the product.
- Respect reduced-motion preferences when choosing pulse/shimmer behavior.
- If a hand-written loading state conveys business meaning better than a geometric skeleton, keep the hand-written state.
- Boneyard handles **loading** only; empty, error, partial-success and retry states still require explicit product UI.

## Design acceptance check

For each data-heavy screen:

1. Does the loading state preserve the final layout and hierarchy?
2. Is layout shift minimal when data resolves?
3. Are fixtures non-sensitive and representative?
4. Are all supported breakpoints captured?
5. Does the screen still have separate empty/error/retry states?
6. Has bone generation been rerun after the latest layout change?
